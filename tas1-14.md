Work ONLY on the purchase distributor-resolution workflow. Do not refactor unrelated code or change the existing purchase architecture.

Remove this behavior completely.

→ medicine selected

→ medicine selected
→ distributor resolved?
   YES → continue existing purchase flow unchanged
   NO  → STOP finalization

        → user selects existing distributor OR deliberately creates the real distributor
        → user continues purchase

IMPORTANT:
- Do not invent a distributor.
- Do not automatically create a distributor.
- Do not change the existing purchase calculation, inventory insertion, invoice structure, or UI layout unless required for this validation.
- Preserve existing valid-distributor behavior.
- Do not modify Catalog Worker.

1. Find every purchase path that can create/use "Default Distributor" or an equivalent fallback.
2. Remove only the fabricated fallback behavior.
3. Keep unresolved distributor state explicit.
4. Add server-side validation so bypassing the UI cannot save the purchase.
5. Add/modify the UI validation so the user knows exactly what must be fixed.
6. Ensure the purchase is NOT written to the database before distributor resolution.
7. Ensure inventory is NOT created/modified when the purchase is blocked.
8. Search for equivalent distributor fallback logic in the affected purchase workflow.

USER EXPERIENCE:
If distributor is missing, the purchase screen must remain usable but clearly show:
"Distributor required before purchase can be finalized."

The user must be able to resolve the distributor without losing the purchase data already entered.

TEST:
A. Valid distributor → purchase works exactly as before.
B. Missing distributor → purchase cannot finalize.
C. Browser/UI bypass → server still rejects it.
D. Confirm no "Default Distributor" record is created.
E. Confirm no inventory is created from the blocked purchase.
